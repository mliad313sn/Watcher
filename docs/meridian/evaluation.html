§1 Method

What it was actually used for

The Watcher 1.1 release — five workstreams closing the gaps that separated a polling-only monitoring platform from the products it competes with — was planned, governed, gated and closed out in Meridian. Programme WCH: SNMP traps, syslog, flow analytics, remote-site proxies, configuration drift.

The entire programme was driven through the REST API, headlessly, without opening the interface once. That is itself a finding.

§2 Benefits

What Meridian does that mainstream PM tools do not

Ranked by how much each one would change a buying decision.

01

The gate refuses. It does not warn.

The first thing that happened when the trap and syslog work was complete:

PATCH /api/projects/PRJ-147/phase {"phase":"Closure"} → 409 1 evidence item outstanding for Gate 1 — Mandate

Jira lets you drag a card to Done. Monday, Asana, Wrike and Smartsheet let you set a status field to anything. Microsoft Project has no concept of an evidence gate at all. In every one of them the gate is a convention a determined person routes around in four seconds.

To get past it we had to file the charter, the architecture dossier, the test evidence and the realisation report, give each a real artefact link, and have each one approved. This is the single reason to choose Meridian. Everything else is good engineering; this is a different product category.

02

Filing evidence and approving it are different acts

POST /api/documents {"status":"Approved"} → 400 A document is filed, then approved — approving is a separate act, so that the trail shows who wrote the evidence and who accepted it

An ownerless document cannot be approved at all, because the independence check compares approver to owner and an absent owner matches nobody. Changing the owner and approving in one call is refused too — that is how an owner signs their own work in two steps.

No mainstream PM tool enforces separation of duties on approvals. ServiceNow SPM and Planview can be configured toward it with workflow effort; here it is the default and cannot be switched off.

03

Evidence must be a thing, on a host named in advance

→ 400 Gate evidence needs its artefact — the link to the piece itself, not only a status
→ 400 No trusted document hosts are configured — name the group's document estate before evidence can be approved

The trusted-host list ships closed. An unconfigured control that waves things through is the failure this product was blocked over, and it shows. In Jira, evidence is a checkbox someone ticks.

04

The audit trail cannot be rewritten, and the database enforces it

-- server/migrations/001_core.sql
CREATE RULE audit_no_update AS ON UPDATE TO audit_event DO INSTEAD NOTHING;
CREATE RULE audit_no_delete AS ON DELETE TO audit_event DO INSTEAD NOTHING;

Not application code the next endpoint could bypass. The audit insert also shares the mutation's transaction, so a change that is not audited does not commit. Reading the trail is itself audited — a row appears saying Audit trail consulted. We have not seen another PM tool do that.

Nuance: DO INSTEAD NOTHING silently ignores an UPDATE rather than raising, so an application bug that tries to rewrite history fails quietly. The data is safe either way.

05

Concurrent edits collide instead of silently overwriting

Every mutable row carries a version, every PATCH must state the version it read, and a second writer gets a 409 — never a silent overwrite. One of the nine build gates is "client PATCH calls that do not name a version", so the discipline cannot rot.

Jira, Asana, Monday and Notion are last-write-wins. If two people edit a risk in the same minute, one loses their work and neither is told.

06

A project arrives able to be run

Creating each project scaffolded eight stages, four gates, four evidence documents and the PM's own resource allocation. The code says why: "A bare project row is not something anyone can run." The gates were already blocking before anything had been typed into them. In Jira you get an empty board.

07

The API is complete enough to run a programme headlessly

Five projects, 56 stages, 25 milestones, 9 RAID items, 20 documents filed and approved, 15 phase advances — all through REST, scripted.

Most PM tools' APIs are a second-class surface where the interesting operations are missing or behave differently. Meridian's is the same surface the UI uses, with the same rules applied in the same place. For an automated or AI-assisted delivery process this is the difference between usable and decorative.

08

It holds itself to a standard it can prove

$ npm test        449 tests, 449 pass, 0 fail
$ npm run audit   nine static gates, all pass
                  · 21 screens × 4 roles = 84 renders, no exceptions
                  · every route matches its published contract
                  · every mutation carries an audit row

A higher verification bar than most commercial PM products can demonstrate — and checkable in ten minutes, because the source is right there.

09

Real earned value, not a progress bar

SPI, CPI, EAC, VAC, TCPI and a forecast finish derived from schedule performance — genuine EVM, behaviour-frozen and tested. Jira, Linear, Asana and Monday have no EVM at all. Smartsheet and Wrike approximate it. This is the real thing.

10

No vendor, no telemetry, no licence check

Three commands and it is running. Apache-2.0 with a patent grant. A default installation makes no outbound network request, and the NOTICE shows you how to verify that.

§3 Gaps

Where it falls short of other PM tools

Stated as a buyer would state them.

It is not where the work happens — and there is no bridge to where it does Biggest objection

Meridian says of itself: "It is not a task manager, a time-and-billing system, an ITSM tool, or an agile team board." Fair. The consequence is concrete: the delivery team's work lives in Jira, Azure DevOps, GitHub or Linear, and Meridian has no native sync to any of them.

Everything we recorded — 56 stage completions, 25 milestones — we recorded twice: once in the engineering repository, once here. Somebody re-enters status, and re-entered status is stale status. This is the objection most likely to kill an adoption.

No chat, no notifications where people already are

No Slack or Teams integration. There is a notification centre and an SMTP path (unconfigured by default), but a PMO tool that cannot post the weekly digest into the channel the programme lives in gets checked less often than one that can.

No mobile

No app, and no installable web app. A sponsor approving a gate from an airport cannot.

No in-app report builder

Fourteen stable SQL views for Power BI, Excel, Tableau and Qlik — an honest, durable answer, better than a proprietary export. But with no BI capability in the PMO there is no drag-and-drop designer here, and Smartsheet or Monday will feel far more capable.

No vendor — restated as a cost

Benefit 10 is also a risk. No support contract, no SLA, nobody on call. The project says so plainly: "If it breaks on a Sunday, you fix it or you wait." Disqualifying for a regulated programme that requires vendor indemnity, and no amount of code quality substitutes for it.

The decision record is mostly in French

Code and interface are bilingual; the twenty-five documents explaining why each decision was taken are largely French. The reasoning is the best thing about this project, and most of it is currently unreadable to most of its potential users.

It has not run a real portfolio for a year

Their own market committee says so. Our use was a full working day of intensive scripted traffic — not twelve months, eight sites and two hundred users. Everything about the design suggests it would hold. Nothing here proves it.

Single instance by default

The embedded database is a single-process engine, and multi-tenant SaaS is explicitly not the model. A real deployment wants PostgreSQL, a second instance and a tested backup — which the project lists as three blocking operational findings that are yours, not the software's.

No resource marketplace or skills matching

Capacity, allocation, rotation, absence and timesheets — more than Jira, roughly Smartsheet's level. Planview and Clarity go considerably further for organisations needing skills-based supply and demand matching.

§4 Findings

Two defects found by using it, both fixed

Patch supplied: docs/meridian/0001-meridian-first-run-and-audit-images.patch

Finding 1

Following the README exactly produces an empty instance BlockerFixed

The README says: "With no DATABASE_URL the server runs PGlite from server/.data/pgdata." It did not. .env.example sets PGLITE_DIR, but nothing loads .env — dotenv is not a dependency and is imported nowhere — so the fallback was an in-memory database.

$ npm run seed
  seeded 12 projects · 10 users · 7 meeting series   ← into memory; dies with the process
$ npm run dev
$ curl localhost:4173/api/auth/accounts
  {"seeded":false,"accounts":[]}                     ← every documented password refused

The failure is silent and total, and nothing in the output suggests what happened. It is the first thing every new user meets.

Fixed by making the code do what the README says, resolved from db.js rather than the working directory. An explicit data directory still wins — including null, which is how the audit harnesses ask for a throwaway instance and must keep doing, or a sweep would overwrite the real book. Plus mkdir -p: PGlite creates the last path element only.

Finding 2

Closing a register item recorded no before-image Fixed

The audit table carries before and after images and the writer supports them — but among the call sites they are passed on deletions and a few exceptional acts, not on ordinary updates. Across the 180 audit rows this campaign wrote, none carried a before-image, including eight Item closed rows.

That is the wrong way round for a register: items are closed constantly and deleted almost never, and "who closed this risk, and what did it say before?" is the first question asked at review. The trail could say a risk was closed and by whom, but not what it had been.

after the fix
"before_json": {"status":"Open","probability":2,"impact":5,
                "response":"Monitor","title":"…","detail":"…"}
"after_json":  {"status":"Closed"}

Both fixes were checked against Meridian's own bar: 449 tests, nine gates and the build all still pass.

§5 Verdict

Not a better Jira

Meridian is a governance instrument, and a genuinely good one.

If what you need is "prove to an auditor in March why this decision was taken, who approved the evidence, and that nobody rewrote the record", it does things no mainstream PM tool does — and it does them by refusing at the moment of the act, rather than reporting afterwards that somebody should not have.

If what you need is "where does my team put their tickets", it is the wrong tool, and it says so itself.

For this programme it was the right choice, and the gate that refused to close PRJ-147 without evidence is the reason. It forced the charter, the architecture note, the test evidence and the realisation report to exist for all five workstreams — documents a self-directed engineering effort would have skipped, and that are now the reason the release can be explained to somebody who was not there.

What would make it adoptable far more widely

  1. A Jira / GitHub / Azure DevOps bridge. One connector that closes a stage when its work item closes. The difference between a PMO tool people maintain and one they abandon — and the only item here that changes the product's category.
  2. Before-images on every update route, not only deletions. Finish what the supplied patch starts.
  3. Slack and Teams delivery for the weekly digest and gate approvals.
  4. English translations of the decision record. The reasoning is the best thing about this project.
  5. A one-page "what breaks if you skip this" operations guide for the three findings the project correctly leaves to the operator: a tested backup, a second instance, a written security policy.
